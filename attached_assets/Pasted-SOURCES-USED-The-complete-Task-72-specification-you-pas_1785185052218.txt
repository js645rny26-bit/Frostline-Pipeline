#72 — Vehicle Doctrine Shadow Architecture

Purpose

Establish a testable architecture separating:

1. vehicle evaluability
2. vehicle-specific viability
3. comparative price-blind ranking
4. final CORE authorization

Do not modify live vehicle selection or current workbook outputs during this task.

Preserve operational behavior

* Keep the existing GAME_TOTAL seed operational.
* Do not change today’s board.
* Do not change future SLATE_BOARD output.
* Do not change projections, thresholds, calibration, lock logic, survival logic, monotonicity, schema, or workbook sheets.
* The new architecture runs in code/tests or shadow output only.

Add VehicleCandidate

Create a typed candidate contract containing:

* vehicle type
* target team, side, pitcher, or player where applicable
* vehicle-specific projection
* vehicle-specific market line
* availability
* data completeness
* viability/evaluability state
* named blocker
* the eight doctrine-ranking attributes

Add evaluateVehicleCandidate(candidate, context)

Return one of:

* VIABLE
* NOT_VIABLE
* NOT_EVALUABLE
* UNAVAILABLE

Rules:

* Missing workload freezes workload-dependent vehicles only.
* Missing team-total projection freezes that team total only.
* Missing starter-prop projection freezes that starter prop only.
* Known opener/bulk chains are evaluated normally.
* Unresolved opener/bulk chains freeze only dependent vehicles.
* No vehicle class receives automatic preference or rejection.

Add rankViableVehicles(candidates)

* Rank only candidates with status VIABLE.
* Use candidate attributes, not vehicle labels.
* Do not use odds or juice.
* Do not use CORE status.
* Do not silently promote unavailable or non-evaluable vehicles.
* If no candidate is viable, return NO_VIABLE_VEHICLE with the controlling blockers.
* When candidates are tied across all criteria, preserve stable input order or return a tie.

Keep authorization separate

Create or preserve a separate function:

authorizeSelectedVehicle(selectedCandidate, context)

The best vehicle may still return NO_CORE because of:

* projection separation
* monotonicity
* lineup state
* unresolved context
* another authorization blocker

The selected vehicle must remain identifiable even when authorization returns NO_CORE.

Required regression tests

1. Either-side eruption
    Full-Game Over ranks first because explicit script-capture and allocation-dependence attributes are superior.
2. One-sided ownership
    Team Total Over ranks first because explicit one-sided offensive ownership and suppression-chain attributes are superior.
3. Traffic without conversion
    Outs Under ranks first because pitch stress and hook pathways are strong while run conversion is weak.
4. Contact-dominant fade
    Hits Allowed Over ranks first because contact access is the dominant supported path.
5. Full-game Under burden
    One unresolved suppression chain makes Full-Game Under NOT_EVALUABLE; an opener label alone does not.
6. Price blindness
    Changing odds or juice metadata does not change candidate viability, ranking, or selected vehicle.
7. Unavailable preferred vehicle
    The highest-ranked viable candidate is unavailable; reroute occurs only to the next independently viable candidate.
8. No viable vehicle
    Return NO_VIABLE_VEHICLE with blockers. Do not force selection.
9. Identical attributes, different labels
    Vehicle type alone cannot affect ranking.
10. Viable but NO CORE
    The best vehicle is selected first, then authorization returns NO_CORE with the applicable blocker.
11. Unknown workload isolation
    Starter prop becomes NOT_EVALUABLE; unrelated total vehicles remain independently evaluable.
12. Unsupported projection protection
    Moneyline, team total, or starter prop cannot reuse a full-game-total projection.
13. Known opener/bulk chain
    Full-Game Under is not automatically rejected solely by role designation.
14. No operational drift
    Existing live pipeline outputs remain unchanged while the shadow architecture executes.
