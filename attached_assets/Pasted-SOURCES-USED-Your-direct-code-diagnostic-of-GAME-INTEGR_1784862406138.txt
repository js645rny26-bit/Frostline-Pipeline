Repair 2: Venue park-factor integration

Commission this now.

Route startingNineResult.park_factors.runs_pct into computeRunMultiplier.

This is cleaner than the offensive repair because the field is already:

* venue-specific
* game-matched
* normalized
* directly expressed as a run modifier

However, I would not automatically discard weather.

Correct hierarchy:

Venue baseline = park runs_pct
Game-day modifier = weather

Park and weather represent different things:

* park factor describes the venue’s structural scoring environment
* temperature, wind, roof state, and precipitation describe that day’s deviation from baseline

So the formula should be conceptually:

Run Multiplier =
Park Baseline Multiplier
× Weather Adjustment

Not:

Park factor instead of weather

Required audit outputs:

* Park_Runs_Pct
* Park_Multiplier
* Weather_Multiplier
* Combined_Run_Multiplier
* Park_Source_Status

The model must avoid double-counting if the supplied park factor already incorporates a live-weather adjustment. Based on your description, it appears to be a venue factor, but that assumption needs confirmation in the source contract.

Approve for development, not commissioning yet.

It does not support an actual lineup-strength calculation without a batter-stat join.

That means the displayed Lineup_Strength = 100 should not survive as though it is meaningful.

Until the player cross-reference exists, do one of two things:

Lineup_Strength = NULL

The first is better. A null with an explicit status is harder to mistake for a legitimate modeled value.
